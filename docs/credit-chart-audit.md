Every source file shares one schema, so the pipeline needs a **single adapter**
(`wbw-standard`) plus a strict schema detector that rejects anything that does
not match, rather than a family of competing adapters.

## Source layout

```
Resort_Info_WBW/
  <State or Country>/
    WBW <Resort Name>/
      <resort_slug>.json     ← credit chart (source of truth)
      CreditChart.png        ← the OCR'd original image (reference only)
```

The `.png` files are the original scanned charts. The `.json` files are the
transcribed data and are the primary source of truth for calculation. Images
are **not** consumed by the pipeline.

## Schema family: `wbw-standard`

Every file has exactly these top-level keys:

```jsonc
{
  "resort": "Havasu Dunes",        // display name (string)
  "state":  "Arizona",             // matches the parent folder
  "source": "CreditChart.png",     // provenance pointer
  "seasons": [ /* … */ ]
}
```

Each **season** object:

```jsonc
{
  "name": "prime",                 // one of: prime | average | slow
  "meaning": "Highly sought after - peak demand",
  "date_ranges": {
    "2026": ["Jan 1", "Mar 13 - Oct 1", "Nov 6 - Dec 31"],
    "2027": ["Mar 12 - Sep 30", "Nov 5 - Dec 31"]
  },
  "rooms": [ /* … */ ]
}
```

Each **room** object:

```jsonc
{
  "type": "1 BR",
  "features": { "kitchen": "full", "accessible": true, "multi_phase": true },
  "credits": { "mon_thur": 850, "fri_sat": 1700, "sun": 1200, "week": 8000 }
}
```

### Fields shared across **all** files
- `resort`, `state`, `source`, `seasons`
- season `name`, `date_ranges` (keyed by year), `rooms`
- room `type`, `credits`
- credit keys: `mon_thur`, `fri_sat`, `sun`, `week` (all four present, all whole numbers > 0)

### Fields that vary
- **Season count** per resort: 3 seasons (64 resorts), 2 seasons (19), 1 season (17).
  Single-season resorts are typically Hawaii / Fiji / year-round "prime" resorts.
- **Room list** length and labels: 56 distinct free-text `type` strings.
- `features`: optional keys `kitchen` (`full` | `partial` | `mini`), `accessible` (bool),
  `multi_phase` (bool). Presence is inconsistent and features do **not** affect pricing.

## Day-of-week → rate mapping (authoritative)

Confirmed from the existing engine (`lib/tripPlanner.js`) and `Claude.md`:

| Day | Rate key | Classification |
| --- | -------- | -------------- |
| Sunday | `sun` | day-specific |
| Monday–Thursday | `mon_thur` | weekday |
| Friday, Saturday | `fri_sat` | weekend |

Weekend nights are **Friday and Saturday**; Sunday is its own day-specific rate.
This is defined per resort in the normalized `rules.weekendNights` — never hard-coded globally in the engine.

## Weekly pricing rule (authoritative)

From `Claude.md` and the existing engine:

> The 7-night `week` rate is applied when a full 7-night block sits **inside one
> season** and the week rate **beats** the nightly sum.

Encoded as `weeklyPricingStrategy: "lowest-valid-rate"` with the documented
constraint that the 7-night block must be single-season. Mixed-season 7-night
windows are **not** given a weekly rate (the official rule for that case is not
present in the source), so they fall back to nightly pricing. This avoids
inventing a rule the charts do not state. See `docs/calculation-rules.md`.

## Known ambiguities / missing data

These are genuine source gaps. The calculator must **not** guess — a stay
touching an uncovered date returns an error/warning rather than a price.

**Coverage gaps** (dates with no season) — 10 resort-years:
- `washington-wbw-long-beach` 2027: **Nov 12–18** uncovered (7 days — `average` ends Nov 11, `prime` starts Nov 19).
- `california-wbw-windsor` 2026: Oct 29 uncovered (1 day).
- `missouri-wbw-lake-of-the-ozarks` 2027: 1 day.
- `new-mexico-wbw-santa-fe` 2026 & 2027: Oct 1 uncovered (1 day each).
- `utah-wbw-moab` 2026, `washington-wbw-deer-harbor` 2026, `washington-wbw-discovery-bay` 2026, `washington-wbw-mariner-village` 2026 & 2027: 1 day each.

**Season overlaps** (a date claimed by 2 seasons) — 3 resort-years:
- `new-mexico-wbw-santa-fe` 2026 & 2027: Nov 12 in both `prime` and `slow`.
- `texas-wbw-stablewood-springs-resort` 2026: Dec 17 in both `prime` and `slow`.

Overlaps are surfaced as warnings; nights on an overlapping date raise an
`AmbiguousSeasonError` at calculation time (never silently pick one).

## Files that cannot yet be parsed safely
None. All 100 files parse and normalize. The 10+3 resort-years above load with
**warnings** but remain active; only the specific ambiguous dates are unpriceable.

## Duplicate names
`La Paloma` appears twice — `California/WBW La Paloma` and `Mexico/WBW La Paloma`.
These are distinct resorts, disambiguated by including the state/country in the
resort id (`california-wbw-la-paloma` vs `mexico-wbw-la-paloma`).

## Existing architecture to preserve
- Vanilla HTML + vanilla JS front end, no build step.
- Express server (`server.js`) serving static files + JSON APIs (`/api/plan-trip`, etc.).
- Existing engine `lib/resortData.js` + `lib/tripPlanner.js` (kept intact; the new
  calculator reuses the same authoritative day/season/weekly rules in an isolated,
  independently-tested `lib/credits/` module).

## Recommended normalization strategy
1. Keep raw files untouched in `Resort_Info_WBW/` (source of truth).
2. One adapter (`wbw-standard`) with a strict schema detector.
3. Normalize into the model in `lib/credits/types.d.ts` / validated by `lib/credits/schema.js`:
   - stable `resortId` = `<state-slug>-<resort-slug>`
   - stable `unitTypeId` = slug of the raw label (meaningfully different labels stay separate)
   - stable `seasonId` = `prime|average|slow`
   - `creditRates`: `weekdayCredits`=`mon_thur`, `weekendCredits`=`fri_sat`,
     `nightlyCreditsByDay.SUNDAY`=`sun`, `weeklyCredits`=`week`
   - `rules`: weekend = Fri/Sat, weekly strategy = lowest-valid single-season week,
     split-season per-night, no check-in-season lock.
4. Emit generated artifacts to `data/generated/` (`normalized-resorts.json`,
   `resort-index.json`, `resorts/<id>.json`, `validation-report.json`).
5. Validation errors block a resort; warnings keep it active but visible on `/data-status`.
